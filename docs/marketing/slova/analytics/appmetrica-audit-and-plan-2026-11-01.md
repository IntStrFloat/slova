## 4. Контракт данных после изменений

### Идентичности и время

- **device_key** — идентификатор AppMetrica из экспорта (UInt64 хранить строкой), не уникальный человек. **install_key** — отдельный эпизод установки: SDK installation ID, если доступен, либо проверенный ключ записи установки. Один device_key нельзя автоматически считать одной установкой за всю историю. Анонимный local player_id — третья сущность; не склеивать устройства по nickname/email.
- Основная когорта A24/Dn — **первые подтверждённые установки**, reinstall/reactivation — отдельные когорты. Классификацию брать из install metadata с документированной семантикой источника; отсутствие ранней истории не делает первую видимую запись первой установкой. Unknown first/reinstall показывать отдельно и исключать из primary new-install метрики с опубликованной долей исключений.
- Событие связывается с install_key по явному installation ID; если его нет — только по валидированной связи device_key и интервалу данного install episode до следующей переустановки. Неоднозначный join остаётся unknown. Версия установки фиксируется в записи эпизода, версия события — отдельно. Псевдоним `sdk_id` существующего анализатора не считать готовым install_key без этой нормализации.
- **event_id** — одна неизменная запись при retry; дедуп в экспорте по SDK identity + event_id. Это не делает UI AppMetrica автоматически exactly-once.
- **business key** — completionId, transactionId, rewardId, attemptId или payment event key. Повтор с новым event_id всё равно не повторяет финансовый/игровой факт.
- Ключи должны проходить реальный лимит: текущий `trackOnce` добавляет имя события к ключу, затем проверяет общую длину ≤96 символов. Длинные составные ID нормализовать в устойчивый короткий ключ с контролем коллизий; boundary tests обязательны. Иначе событие будет отвергнуто до постановки в очередь.
- **levelKey** — campaign:globalId или daily:dateKey + content identity; world/route/pack отдельно. Один levelId без версии недостаточен после замены контента.
- **attemptId** сохраняется при background/restart/resume; новый только при действительно новой попытке. Историческое восстановление без известного старта отмечается left-censored, а не искусственным стартом.
- **session_id** в текущем коде — собственная 30-минутная сессия. SDK session и время SDK из «Вовлеченности» вести отдельно. Не менять session timeout задним числом: версия определения и дата разрыва ряда обязательны.
- **occurred_at** — время реального действия; **observed_at** — восстановление/наблюдение; **sdk_handoff_at** — передача SDK. Клиентские часы не становятся доверенными от переименования.
- **actionDay** — день действия UTC+3; **dateKey** — дата daily; **periodId** — личная неделя; **eventInstanceId** — конкретный цикл/марафон.

Поле `first_open` сейчас означает новый локальный профиль. Канонический первый запуск установки берётся из SDK install metadata. Они не взаимозаменяемы.

### Общие обязательные поля

Для client custom v3: `event_id, schema_version=3, occurred_at, time_trust, app_version, app_build, platform, environment, release_channel, consent_state, producer, analytics_session_id`. Общий маркер payload — только `schema_version`; storage version живёт отдельно. Локальную анонимную идентичность передавать только если необходима для join; доступ к ней ограничен, в ежедневном отчёте нет индивидуальных ID.

Для server envelope обязательны `event_id, schema_version=3, server_build, producer=backend, environment, occurred_at, effective_at, time_trust, binding_state` и доменный business key. Серверное продление/возврат может происходить без приложения: analytics_session_id отсутствует, клиентские app/build/installation при наличии передаются только как `originating_*` с доказанной связью. Не заполнять их текущей версией сервера или фиктивной сессией. Допустимость выгрузки в AppMetrica определяется consent/binding policy; backend ledger остаётся отдельным источником истины.

Для gameplay дополнительно: `mode, levelKey, levelId, world, route_id, content_version, content_fingerprint, onboarding_version, config_version, attemptId`. Для UI: `screen, element_id, action, entry_source, outcome`. Для денег: integer amount в минимальной единице, currency, transaction business key, source/sink, balance_before/after. Для эксперимента: immutable assignment + exposure отдельно.

Сводки активного времени не должны сами продлевать игровую сессию. Ротация собственной сессии опирается на foreground и действия игрока; telemetry flush, восстановление наград и фоновая доставка не создают новую play-сессию. Для чтения/обдумывания решения сохранять raw foreground gameplay time и отдельно idle-adjusted time с явным порогом, чтобы не списать размышление в отсутствие интереса.

Каждое событие имеет owner, trigger, required/optional fields, enum/range, dedupe key, visibility rule, denominator role, schema version и QA case. Каталог ниже определяет смысл; реализация переносит его в проверяемые типы/fixtures.

Сейчас общий context по умолчанию содержит `configVersion=local-v1`, `contentVersion=unknown`, а experimentVariants пуст. В lifecycle конкретная contentVersion передаётся отдельно, но это не делает все события полноценно версионированными. В новой схеме брать реальную версию/хэш загруженного контента и политики; неизвестное значение сохранять как unknown, не придумывать вариант эксперимента.

Не отправлять введённые слова, nickname, email, коды восстановления, токены, полные URL, свободные exception/stack без фильтрации, координаты касаний. Для ошибочного слова достаточно outcome/length/answer index/контекст; для жалобы при её будущем подключении — category и content ID.

### Миграция без потери истории

1. Зафиксировать список старых имён и payload, rollout build и даты доступности.
2. **Разделить storage version и event schema version.** Текущий reader принимает только v2: простая замена константы на 3 отбросит очередь. Читать/безопасно доотправить разрешённые v2 либо мигрировать явно; opt-out имеет приоритет.
3. Обновить `scripts/analyze-retention.cjs`: сейчас распознаёт envelope только при schema_version===2 (`:41`). Поддержать flat v3, сохранить legacy normalizer.
4. Не отправлять старый и новый канонический факт параллельно в production без marker и срока отключения. Для callback рекламы новое имя оправдано изменением смысла.
5. Старые `level_start/level_complete/session_start/word_found/wrong_word/coins_spent` оставить в истории. Mapping — только с достаточными параметрами; неоднозначность попадает в quality, а не угадывается.
6. Пересчитать только то, что исходные данные действительно позволяют. Недостающее active time, реальный момент старой победы, показ UI и отсутствующие деньги задним числом не восстанавливаются.

### Частота и объём

Полнота означает покрытие значимых действий и результатов. Не логировать каждое касание/кадр/букву диска. `word_submit_outcome` остаётся единым потоком завершённых вводов. Низкоуровневый `gameplay_action` можно перевести на один квалифицирующий факт сессии/дня после сохранения определения Dn_play; период миграции обозначить явно.

Ключевые факты (start, completion, transaction, reward, assignment/exposure) не сэмплировать. Подробную диагностику допускается ограничивать только явно: sample_rate/decision_unit, неизменное назначение, отдельные отчёты. UI actions собирать по утверждённым контролам; уже инструментированное действие не дублировать вторым каноническим событием.

На базовом тарифе официально описан лимит **3 250 000 custom events за 24 часа суммарно по организации**, с возможной задержкой через буфер. Фактический тариф/общую нагрузку организации в этом аудите не проверяли; ежесуточный аналитик должен наблюдать лимит и lag. [Ограничения AppMetrica](https://yandex.ru/support/appmetrica-io/ru/common/limits).

## 5. Как анализировать и принимать решения

### Витрины и источники

1. AppMetrica Events/Reporting — быстрые агрегаты и разрезы; Logs API или согласованный экспорт — последовательности, пересечения, дедуп, точные окна.
2. SDK installs/sessions — календарь когорт, источник привлечения, частота входов. `source=direct/resume` из custom session не источник рекламы.
3. Domain events — gameplay/экономика/награды; static content catalog — характеристики пазлов.
4. Backend verified ledger — платежи, продления, возвраты, entitlement. У рекламы — один проверенный Ad Revenue канал и сверка с отчётом сети.
5. Release/experiment log — изменения кода, контента, рекламы, политики и измерения.

Не выдавать наличие API в документации за действующий доступ. Для ежедневного запуска сначала проверить read-only доступ/пагинацию/quota/export fields. Секреты держать вне git; если raw экспорт недоступен, использовать UI-агрегаты с ограниченным классом решений.

Базу уже даёт `scripts/analyze-retention.cjs` и [runbook](../../../runbooks/retention-analysis.md); переиспользовать нормализацию и тесты.

### Паспорт основных метрик

Общие исключения: тестовые сборки/устройства, неверная схема, дубли, события после opt-out, недозрелые окна. Не удалять «неудобных» пользователей после воздействия. По каждой оценке хранить numerator/denominator, unit, окна, as_of, watermark/lag, definitions version, query hash, exclusions и missing share.

| Метрика | Точное определение и источник | Решение |
|---|---|---|
| Активация A24 | Первые подтверждённые install_key с хотя бы одной самостоятельной победой на L2–L5 за первые 24ч / все такие измеримые install_key с полными 24ч; reinstall отдельно | Улучшать объяснение/первые уровни; не считать L1 безусловной самостоятельной ценностью |
| Intro conversion | Уникальные установки, последовательно достигшие заданного шага в 24ч / установки, вошедшие в предыдущий шаг; отдельно first field latency | Исправить конкретный провал; различать latency/error/help/отказ |
| D1/D7/D30_open | Установки с foreground SDK session в календарный Dn МСК / install cohort с полным Dn | Частота возвращений |
| D1/D7/D30_play | Те же когорты, но в Dn есть ручной submit либо успешно применённая добровольная помощь; бонус/показ рекламы не считаются игрой | Проверить, возвращаются ли играть |
| DAU/WAU/MAU_play | Уникальные SDK identities с play за 1/7/30 полных календарных дней | Масштаб и регулярность, без суммирования дневных uniques |
| Stickiness | Среднее DAU_play за 30 полных дней / уникальное MAU_play того же окна | Динамика привычки; не прибыль |
| Sessions/user | Foreground SDK sessions / unique active SDK users в одном окне; custom sessions отдельно | Частота и влияние коротких выходов |
| Активное время | Сумма foreground gameplay интервалов без рекламы/меню/фона, плюс idle-adjusted вариант с опубликованным порогом; p50/p90 на игрока/сессию | Сложность/вовлечённость; долго не всегда хорошо |
| Solve72 | Unique SDK×puzzle с победой за 72ч от первого подтверждённого старта / все такие пары с полным 72ч | Сложные уровни, контент, подсказки |
| Attempt solve | Уникальные attemptId из зрелого знаменателя, завершённые в течение 72ч от их старта / уникальные started attemptId с полным 72ч; поздние победы отдельно, resume не новый attempt | Ретраи/сбои отдельно от уровня |
| Incomplete72 | 1−Solve72; отдельно explicit exit и return within72 | Не называть окончательным уходом; окончательный churn этим не доказан |
| Ошибки и помощь | Invalid submissions / all manual submissions; help users / started users того же пазла; время до следующего успеха | Где непонятные слова/управление; сравнивать контент и skill/progress |
| Доступность feature | Eligible users → actually exposed users → entered users → completed users в фиксированном окне | UI discoverability отдельно от пользы функции |
| Daily repeat | Первый daily winner вернулся и решил daily в другой день в пределах 7 полных дней / первые daily winners с полным окном | Привычка; учитывать carry date и повтор шаблона |
| Дефицит монет | Пользователи с denied hint: insufficient / пользователи, запросившие платную помощь | Цена подсказок и источники валюты |
| Экономический баланс | Σ committed credits−Σ committed debits; проверка balance_before+delta=balance_after | Потери/дубли; дефицит/накопление по progress cohort |
| Reward integrity | Уникальные подтверждённые награды, не выданные в SLA / unique confirmed rewards с полным SLA | Исправление выдачи, без продуктового A/B |
| Ad opportunity funnel | Eligible opportunity → request → loaded → shown → impression → closed/reward, join по opportunity/request/impression IDs | No-fill, latency, ошибки, frequency cap |
| Rewarded grant rate | Unique rewards persisted / unique provider reward confirmations | Надёжность; не смешивать с request→reward opt-in |
| Ad load | Fullscreen impressions / active gameplay hour; ads/session отдельно по типу | Баланс дохода и Dn_play; причинный вред проверять тестом |
| ARPDAU | Ad revenue + подтверждённые платежи−возвраты за день / DAU того же определения; отдельно каждый источник | Доходность активности, неполный доход → unknown |
| Cohort ARPU_H | Revenue_H когорты / исходный размер install cohort с полным H | Сравнение источников, ушедшие остаются в базе |
| ROAS_H | Атрибутированная revenue_H / совместимые расходы привлечения этой когорты | Не считать неизвестные расходы нулём; gross/net подписать |
| Checkout conversion | Unique server-confirmed paid invoices / unique created invoices с завершённым окном статуса | UX/платёжные ошибки; отсутствие invoice из custom events не доказательство отсутствия счетов |
| Renewal | Успешно продлённые / подписки, срок продления которых наступил, с полным grace/retry | Надёжность и ценность подписки |
| Notifications | Qualified gameplay after open / delivered prompts с известным delivery, отдельно consent и route | Техническая воронка; uplift только holdout |
| Stability | Crash-affected users / active users; save failure users / users with save attempt | Регрессии по build/OS/device, не по числу повторных ошибок |

Для save failure denominator нужны все попытки сохранения, включая успешные: `technical_operation(stage=summary)` содержит cumulative attempts/successes/failures по operation и сессии с revision; конечная витрина берёт последнюю revision, не сумму. Детальные failure/recovered события дают диагностику. Если summary отсутствует из-за kill/потери данных, полнота знаменателя неизвестна и доля не публикуется как полная.

Для рекламы opportunity_id создаётся при проверке возможности конкретного показа; policy eligibility/skip фиксируется для каждого используемого формата. request_id создаётся **до** вызова загрузки SDK и передаётся через `ad_lifecycle(stage=requested)` во все связанные callbacks. Не рассчитывать этот join по `ad_request_ads_sdk`, пока общий correlation key с ним не подтверждён.

AppMetrica позволяет различать календарный retention и 24-часовые окна; сохранять выбранную методику. Встроенная длительность сессии может быть не определена до следующей активности. [Retention](https://appmetrica.yandex.ru/docs/ru/mobile-reports/retention-report), [Вовлеченность](https://appmetrica.yandex.ru/docs/ru/mobile-reports/engagement-report).

### Обязательные разрезы

Версия установки и версия события — разные поля. Дополнительно: app_build, analytics schema, content version/fingerprint, intro-v2/legacy, new/returning, campaign/daily, уровень/маршрут/механика, install source/tracker/campaign, country/store, Android/устройство, notification source, eligibility и experiment assignment/exposure. Unknown — отдельная категория.

Срезы по skill/progress/подписке, возникшие после экспериментального воздействия, не использовать как основной causal comparison: это может вносить смещение.

### Правила решения

| Сигнал | Сначала исключить | Следующее действие |
|---|---|---|
| Упала активация | Сломанный старт/SDK, новая схема, источник трафика, неполные24ч | При подтверждённой технической ошибке — fix; иначе тест конкретного шага intro |
| Провал Solve72 на уровне | Content replacement, малая/незрелая база, legacy IDs, restore | Проверка пазла и 3–5 наблюдений игры; затем ограниченный тест сложности/подсказки |
| Выросло время/ошибки | Idle/background, другой уровень, подсказка | Улучшить понятность, не оптимизировать длительность саму по себе |
| Реклама даёт деньги, retention хуже | Состав когорт, caps, версия, ошибки | Предрегистрированный тест frequency cap; guardrails D7_play и reward integrity |
| Мало входов daily | Доступность после L5 и реальный показ CTA | Тест видимости CTA; не вывод о бесполезности daily |
| Пользуются daily и чаще возвращаются | Самоотбор активных игроков | Holdout/рандомизация приглашения, не причинный вывод из корреляции |
| Много subscription_error | stage/reason/status refresh/background/test vs live | Техническая диагностика; цена/оффер меняются только после исправления пути |
| Платежи есть, AppMetrica revenue пуст | Привязка identity/currency/bridge/automatic integration | Сверка ledger; не решение «монетизация не работает» |
| События пропали | Тариф/lag/сервис/permission/schema/deploy | Data incident; продуктовые решения зависимой области заморожены |

Ежедневные колебания — повод проверить, а не повод ежедневно менять игру. Для наблюдений показывать числители/знаменатели и интервалы. Для эксперимента заранее выбрать единицу рандомизации, главную метрику, минимально полезный эффект, MDE/мощность, срок, защитные метрики и правила остановки. Фиксированный тест не заканчивается при первом удобном p-value.

## 6. План реализации и приёмка

### Этап A — контракт и измерительная база

Владелец: разработчик analytics/native; аналитик проверяет определения.

- Создать каталог типов/fixtures рядом с `src/features/analytics`, сверить с данным драфтом; public API track/trackOnce сохранить.
- Исправить DQ-01/02/03/04/05 и migration v2→v3. Затрагиваемые файлы: `privacy.ts`, `index.ts`, `src/core/native/appmetrica.ts`, native module, config-plugin, bootstrap/settings.
- Не вводить новую зависимость или вторую аналитику; версия SDK не обновляется без проверки необходимости. Совместимость native зависимостей проверить по resolved Gradle graph и актуальной документации, а не только package.json.
- В актуальной [справке Yandex Mobile Ads SDK 8](https://ads.yandex.com/helpcenter/en/dev/android/quick-start) указан AppMetrica SDK 8.6.0+. В проекте объявлен 8.3.0; проверить фактически разрешённую Gradle версию и применимость требования к используемой версии Ads. Это основание для проверки совместимости, не доказательство поломки и не команда автоматически обновить зависимости.
- Приёмка: payload fixtures для каждого события; тест отказа/возобновления/рестарта; legacy queue survives; environment не unknown в тестовом сценарии.

### Этап B — игровой путь и экономика

Владелец: разработчик game/domain.

- `puzzleLifecycle.ts, persistence.ts, settlement.ts, game.tsx, features/hints, currency, wheel, NoCoinsModal`.
- Добавить pause/exit/checkpoint, реальное active time всех попыток, помощь, подтверждённые транзакции и wheel flow.
- UI coverage через shared screen/action helper, без переписывания экранов; CTA intent не заменяет committed result.
- Приёмка: процесс убит посередине/после victory/до grant/после grant; offline→online; повторный тап; >512 dedupe; миграция; расход монет сходится; закрытие без callback остаётся unknown.

### Этап C — возвраты, контент, реклама и подписка

Владельцы: game/ads + backend в разных модулях.

- `retentionEvents.ts, retention/model.ts, marathon/*, dailypuzzle/*, notifications/*`: исходное время и eligibility/exposure, марафонные факты.
- `yandexAds.native.ts, AdBanner.native.tsx, rewarded.ts`: callback correlation и один Ad Revenue канал.
- `backend/runtime/billing*.cjs, robokassa.cjs, subscription.ts`: надёжные финансовые события/outbox, идемпотентность, restore/cancel/renewal/refund.
- Backend «Слова» остаётся изолированным; **не трогать bloxx-***.
- Приёмка: no-fill, load/show failure, close before reward, reward then app kill, duplicate provider callback, delayed payment, refund/renewal without app launch, отсутствующая identity.

### Этап D — витрины, кабинет, ежедневный анализ

Владелец: аналитик/инженер данных.

- Привести экспорты к имеющемуся JSONL contract; добавить финансовые и UI витрины, явные freshness/watermarks, lineage и checks.
- Расширить normalizer явными device_key/install_key и first/reinstall policy: тесты нескольких установок на устройстве, сброса local player_id, отсутствующей install history и неоднозначной связи. Переиспользование существующего скрипта не означает, что эта политика уже реализована.
- Настроить в AppMetrica сохранённые отчёты: качество данных; intro; уровни/помощь; daily/quests/events/collection; экономика; ads; subscription; stability.
- Для последовательности действий использовать воронки с согласованным окном, а не деление двух таблиц uniques. Возможности отчёта описаны в [документации воронок](https://appmetrica.yandex.ru/docs/ru/mobile-reports/funnels-report).
- Запустить аналитика сначала в режиме диагностики качества. Product decisions разрешать отдельно для валидных областей; ждать зрелости D7/D30.
- Приёмка: повторный запуск на одном immutable input/as_of даёт тот же результат; incomplete day excluded; late arrivals пересчитывают прошлые окна с новой revision; при недоступном источнике нет нулей/ложного успеха.

### Набор проверок

Для реализации: `npm run lint`, `npm run typecheck`, профильные Jest suites, `node --test backend/scripts/__tests__/retention-analysis.test.cjs`, backend tests при изменении billing; сравнить baseline warnings отдельно. Не требовать успешности несвязанных незакоммиченных изменений без диагностики их владельца.

Native QA — один зарегистрированный AVD «Слова» по Android AVD policy или имеющееся устройство, переиспользование, никаких новых AVD по каждому кейсу. Debug/Test AppMetrica или разрешённый фильтруемый QA-контур. Не создавать реальные оплаты и не менять бюджет для проверки событий.

После реализации — подписанный `.aab`, прежний release.jks, versionCode увеличивается перед загрузкой в RuStore; подпись/сертификат проверить. Сам этот драфт не публикует сборку.

**Definition of done:** каждое доступное действие из карты имеет intent/result или явное обоснование, все критичные доменные факты устойчивы к retry, payload проверен после native boundary, test traffic отделён, opt-out соблюдён всеми производителями, события реально дошли в тестовый кабинет, метрики воспроизводимы из выгрузки, подписана версия схемы и rollout date. Запись в локальный лог не считается приёмкой доставки.

## 7. Какой первый цикл решений оправдан сейчас

1. **Исправление измерения:** native opt-out, QA separation, per-event payload, корректные ad/assistance semantics и ledger — приоритет перед масштабированием событий.
2. **Диагностика:** 427 subscription_error у 141 пользователя разложить по stage/reason/version и backend evidence. Пока не менять цену на основании этой суммы.
3. **Контент:** проверить уровни с достаточной зрелой базой через existing normalizer. Само превышение completed над started не доказывает баг прохождения.
4. **Эксперименты:** подготовить тест понятности проблемного шага intro, затем тест daily CTA или рекламной частоты; выбирать по валидным данным, не запускать всё сразу.
5. **Автоматизация:** только после подключения read-only источников и quality gates применить [бриф аналитика](daily-analyst-brief-2026-11-01.md). Расписание в этом аудите не создано.

## 8. Доказательства и ограничения

- E01 observation: live Events 6321823, 01.11.2026, 101 строка, JSON рядом; неполный день, неатомарность, неизвестный app timezone.
- E02 observation: текущие callsites/AST — 98 имён; ссылка на аудит кода; code != installed release.
- E03 observation: текущая карта функций; доступность отдельных legacy routes не подтверждена.
- E04 observation: **7 suites / 46 tests passed** у существующей analytics/bootstrap/plugin базы. Есть предупреждения bootstrap mock при marathon recovery; это не доказательство production crash.
- E05 platform_fact: официальные страницы Events, SDK methods, limits, retention, engagement и funnels по ссылкам выше, проверены 01.11.2026.
- E06 hypothesis: часть шумного потока можно сократить без потери решений; проверить rollout и сравнимость Dn_play.
- E07 hypothesis: subscription_error требует продуктово-технической диагностики; причина без параметров/ledger неизвестна.

Не проверялись native packet-level доставка/opt-out, полный financial ledger, конкретные платежи, live payload всех имён, атрибуционные окна аккаунта, app timezone и доля QA. Отсутствие этих проверок ограничивает решения соответствующих областей, но не отменяет подтверждённый каталог и план.
