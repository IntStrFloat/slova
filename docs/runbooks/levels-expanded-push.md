# Одноразовый пуш: теперь 1000 уровней

Состояние: **draft, не отправлено**. Никакого расписания, фонового sender или автоматического запуска после деплоя нет.

## Готовая кампания

| Поле | Значение |
|---|---|
| Campaign id | `levels-expanded-1000-v1` — не менять при повторной подготовке |
| RuStore topic | `slova_levels_expanded_1000_v1` |
| Заголовок | Теперь в игре 1000 уровней! |
| Текст | Добавили ещё 500 уровней. Возвращайся за новыми словами! |
| Переход | Главная `/`, через существующий allowlist маршрутов |
| Аудитория | Включены уведомления; целый `currentLevel` от 500 до 1000 включительно |
| Payload | `backend/scripts/levels-expanded-1000.campaign.json` |

Победа на 500-м уровне сохраняет `currentLevel = 501`, такой игрок включён. Игроки с `currentLevel = 1001`, уже закончившие расширенную кампанию, исключаются. SDK-топик привязан к токену установки, а не к учётной записи: одно уведомление на человека с несколькими устройствами не гарантируется.

## Откуда берётся аудитория

Новая версия клиента подписывается через существующий RuStore SDK, когда игрок открывает приложение, меняет прогресс/настройки или возвращается из фона. Без согласия приложение не создаёт токен для этой кампании. На Android 13+ проверяется системное разрешение; при отказе токен удаляется. При смене токена подписка регистрируется заново. Сериализация операций не даёт незавершённой подписке пережить последующее удаление токена при выключении уведомлений.

**Ограничение старой версии:** до этого изменения клиент не регистрировал топик, а backend не сохранял push-token и согласие. Нельзя получить адресную аудиторию просто из списка серверных профилей с уровнем 500. Старый игрок попадёт в топик только после открытия обновления с активными пушами. Если он откроет его уже после публикации пуша, отдельной догоняющей отправки не будет. Нельзя подменять этот сегмент отправкой всем пользователям.

Размер аудитории backend не знает. Успех API-публикации не подтверждает количество подписчиков или доставку конкретному игроку. До production-запуска отдельно проверить подписку на реальном Android в тестовом push-проекте и убедиться, что целевая аудитория действительно начала открывать новую сборку.

## Подготовка без отправки

Достаточно Node.js из проекта; новых зависимостей нет. Указать **production push project id**, а не package name. Он должен совпадать с `EXPO_PUBLIC_RUSTORE_PUSH_PROJECT_ID` опубликованной подписанной Android-сборки.

```powershell
$env:RUSTORE_PUSH_PROJECT_ID = '<production-push-project-id>'
node backend/scripts/levels-expanded-campaign.cjs --dry-run
```

Вызов без флага также является dry-run. Он печатает адрес и тело будущего запроса, не обращается к RuStore, не запрашивает сервисный токен и не резервирует кампанию. Отсутствие/неверный project id вызывает ошибку.

Проверка заготовки:

```powershell
npx jest src/features/notifications --runInBand
node --test backend/scripts/__tests__/levels-expanded-campaign.test.cjs
```

## Ручной запуск после отдельного решения об отправке

1. Проверить опубликованную Android-сборку с 1000 уровнями и её `versionCode`. Проверить реальный push на Android в отдельном тестовом RuStore-проекте: уровни 499, 500, 501 и 1001; отказ в приложении и Android; переход на главную из фона и после холодного старта.
2. Выбрать один операторский хост и постоянную локальную папку состояния **вне git**. Хранить и резервировать эту папку; всем операторам использовать тот же хост и путь. Проверить отсутствие записи `levels-expanded-1000-v1.<project-id>.json` и отсутствие предыдущей ручной публикации этой кампании в RuStore. Учесть quiet hours и остальные кампании.
3. Передать сервисный токен через локальное окружение. Не записывать его в app config, JSON кампании, git или команду с буквальным секретом. Указать `SLOVA_PUSH_CAMPAIGN_STATE_DIR` абсолютным путём и `SLOVA_PUSH_RELEASE_VERSION_CODE` номером проверенного релиза.
4. Только после решения отправить выполнить один раз:

```powershell
node backend/scripts/levels-expanded-campaign.cjs --send
```

Обязательное окружение: `RUSTORE_PUSH_PROJECT_ID`, `RUSTORE_PUSH_SERVICE_TOKEN`, `SLOVA_PUSH_CAMPAIGN_STATE_DIR`, `SLOVA_PUSH_RELEASE_VERSION_CODE`. Наличие переменных само по себе ничего не запускает; нужен явный `--send`.

Скрипт атомарно создаёт запись `attempted` и сбрасывает её на диск **до** HTTP-запроса. Успешный ответ отмечается `accepted`, HTTP-ошибка — `rejected`, сетевая неопределённость — `unknown`. Повторный или параллельный запуск при существующей записи не отправляет ничего. Таймаут — 30 секунд; автоматических повторов нет.

При `unknown`, `rejected` или оставшемся `attempted` сначала сверить результат с RuStore. **Не удалять запись и не менять campaign id/папку/хост ради повторного запуска.** Принятый провайдером запрос мог быть доставлен, даже если оператор не получил ответ. Запуск с другой папкой или напрямую из консоли обходит локальный запрет: так эту кампанию не дублировать. `accepted` подтверждает только приём запроса RuStore, не exactly-once доставку.

## Основание

- [RuStore React Native Push SDK: подписка и отписка от топика](https://www.rustore.ru/help/sdk/push-notifications/react/6-0-0). Сигнатуры также проверены в установленном `react-native-rustore-push` 6.9.1 (`src/index.tsx`, Android `RustorePushModule.kt`).
- [Официальный RuStore API публикации в топик](https://www.rustore.ru/help/sdk/push-notifications/topic-notifications): endpoint `/v1/projects/{project_id}/topics/{topic}/publish`, Bearer service token, тело `message.notification`.

Установленный провайдер остаётся RuStore 6.9.1. Expo Push, дополнительные native SDK, хранение токенов на backend и серверный планировщик не добавлялись.
