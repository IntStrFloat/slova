До этого единственное локальное техническое письмо было принято SMTP 8 октября; доставка во входящие и реальные напоминания игрокам не проверены.

Причина прежних проверочных таймаутов локализована на VPN-маршруте этого компьютера: `tun0` направляет соединения к серверу через VPN; сервер получает SYN и отправляет SYN-ACK, но подтверждение не приходит. UFW разрешает 22/80/443, в Timeweb нет блокирующей группы firewall, локальные HTTP/HTTPS исправны. При работающем VPN разовые TCP-сокеты, направленные через физический интерфейс Windows опцией `IP_UNICAST_IF`, успешно получили публичные **200** для `/api/health`, `/api/billing/catalog` и `/api/billing/manage` с проверкой сертификата. Каталог: `available:false`, `mode:live`. Таблица маршрутов и VPN не изменялись. Это подтверждает доступность с прямого пути, но не исправность всех VPN-маршрутов.

По просьбе владельца подготовлен `scripts/slova-network-tunnel.py` для локального подключения к SSH/HTTPS Slova через выбранный интерфейс при работающем VPN. Автоматическая проверка безопасности отклонила запуск фонового туннеля («blocked by policy»); слушатели не запускались, работоспособность пересылки не заявляется. ### Чеки НПД: повторная проверка

[ЮKassa прямо указывает](https://yookassa.ru/developers/using-api/changelog) прекращение своего сервиса чеков самозанятых при платежах и возвратах с **29 декабря 2025**. В [текущей инструкции по чекам](https://yookassa.ru/developers/payment-acceptance/receipts/basics) для самозанятого указаны регистрация дохода в «Моём налоге» и передача чека покупателю. Поле `fiscalization_enabled:false` в ответе конкретного магазина не заменяет это общее документальное подтверждение. **11 октября в 15:38 МСК бот поддержки в авторизованном кабинете подтвердил закрытие сервиса, отсутствие планов возобновления и доступность партнёрских чековых решений для юрлиц/ИП, кроме НПД.** Отдельно запрошен сотрудник для вопроса согласования Android-скриншотов. Свидетельство — `yookassa-npd-confirmation.png`.

Минимум переделок — сохранить ЮKassa и формировать/передавать чеки через «Мой налог» вручную. Для автоматических продлений это требует постоянной операционной работы: [ФНС](https://npd.nalog.ru/faq/?from=index) различает сроки для электронных средств платежа и других безналичных расчётов; нельзя обещать универсальную выдачу всех чеков раз в месяц.

Из проверенных вариантов автоматизации проще единая интеграция **Robokassa + «Робочеки СМЗ»**: [официальная страница](https://robokassa.com/online-check/robocheck-smz/) подтверждает самозанятых без ИП, автоматическое формирование/передачу чеков для платежей через Robokassa и бесплатность сервиса чеков. Это требует смены платёжного провайдера, не является отдельным чековым API для текущей ЮKassa. По [базовому тарифу](https://robokassa.com/payments/tarify/) и [приложению №4 договора](https://docs.robokassa.ru/media/1285/dogovor_robokassa.pdf): карты РФ 3,9%, СБП 3,5%; условия будущего индивидуального договора пока не проверены. [Автоплатежи поддерживаются](https://robokassa.com/solutions/industry/platezhi-po-podpiske/), но возможность подключения рекуррентов именно физлицу НПД без ИП для Android-игры нужно подтвердить отдельно. Оснований называть провайдера самым популярным по доле рынка нет.

Смена провайдера, переход на ручные чеки или отказ от автопродления не выполнялись. Рабочий процесс чеков ещё не выбран/не подключён; программный запрет live-продаж остаётся.

## Что реализовано

- Hosted checkout ЮKassa открывается через установленный expo-linking. Платёжные ключи находятся только на backend; новые зависимости не добавлены.
- Backend хранит отдельный журнал `/var/lib/slova/billing.json`. Строгий режим не подменяет повреждённый журнал пустым; записи сохраняются атомарно с fsync. Нужен один экземпляр backend.
- Идемпотентная попытка сохраняется до запроса провайдеру. Уведомление/возврат в игру не является доказательством оплаты: backend получает платёж у ЮKassa и сверяет сумму, валюту, режим, владельца и идентификаторы попытки.
- Подтверждённый срок проверяется при запуске/возврате в игру и истекает даже без интернета. Он не превращается в бессрочное отключение рекламы.
- Автопродление выполняется backend; отмена останавливает новые попытки, оплаченный срок остаётся. Уже отправленный провайдеру платёж может завершиться после отмены.
- Код восстановления позволяет перенести подписку на новый профиль и отменить автопродление вне приложения через `/api/billing/manage`. В журнале хранится хеш кода. Новый код выдаётся только по явному запросу владельца; прежний перестаёт работать.
- Подтверждённый возврат прекращает автопродление и отзывает неиспользованный оплаченный срок. Повторное уведомление не отзывает его второй раз.
- Покупки отключены в сборке Yandex Games. Старые заглушки RuStore не выдают оплаченный доступ.

## Настройка backend

Шаблон — `backend/deploy/backend.env.example`; секреты остаются в `/opt/slova/backend.env` с правами 600. `BILLING_ENABLED=0` по умолчанию. Для live нужны `BILLING_MODE=live`, `BILLING_LIVE_READY=1`, заполненные сведения продавца и настроенный live-сервис уведомлений. Пока реальный адаптер НПД не реализован и не проверен, `backend/index.cjs` безусловно блокирует боевые продажи. Старый `BILLING_RECEIPTS_READY` игнорируется: флаг не может подменить выдачу налогового чека.

Для Timeweb задать `BILLING_NOTICE_PROVIDER=timeweb`, `BILLING_NOTICE_SENDER` (адрес ящика или `Слова <billing@домен>`), `TIMEWEB_MAIL_USERNAME` (полный адрес того же ящика), `TIMEWEB_MAIL_PASSWORD`, `BILLING_SUPPORT_EMAIL` и `BILLING_NOTICES_DATA_PATH=/var/lib/slova/renewal-notices.json`. SMTP использует только `smtp.timeweb.ru:465` с проверкой TLS. Пароль не помещать в git, клиент или журнал команд. В test-режиме настоящий SMTP не отправляет уведомления: тесты подставляют транспорт test.

Очередь начинает напоминание за 72 часа до окончания срока. Продление требует подтверждения приёма письма SMTP-сервером и ожидания минимум 24 часов. Это подтверждает приём письма сервером, а не попадание во входящие. При поздней отправке дата списания переносится отдельно от оплаченного срока: ожидание письма само по себе не продлевает доступ. При отмене, смене получателя или условий старое подтверждение не разрешает новый платёж.

SMTP не гарантирует дедупликацию. Неопределённый исход начиная с команды DATA, повреждение журнала или сбой записи после приёма письма требуют ручной сверки; автоматическая повторная отправка и списание блокируются. Нельзя стирать запись, менять ключ или сбрасывать `firstSentAt`, чтобы обойти блокировку. Явный временный отказ SMTP допускает ограниченный повтор; окончательный отказ останавливает отправку.

`YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY` не помещать в клиент, EXPO_PUBLIC-переменные, вывод команд или git. Адаптер требует test_ ключ в test и live_ ключ в live; другой формат отклоняется до запроса. При необходимости другого официального формата сначала подтвердить режим магазина через API провайдера и пересмотреть проверку, сохранив отказ при несовпадении режима.

Разделять тестовый и боевой журнал: например `billing-test.json` и `billing.json`. При переходе режима никогда не переносить тестовые доступы/способы оплаты в боевой журнал. Копии журнала сохранять защищённо вместе с backend env; потеря журнала означает потерю истории попыток и восстановительных кодов.

При неопределённом результате без provider payment ID повтор допустим только с прежним ключом в ограниченном окне (23 часа). После этого — ручная сверка у провайдера; запрещено сбрасывать попытку или создавать новый платёж вслепую.

Уведомления в ЮKassa: `/api/billing/webhook`, события `payment.succeeded`, `payment.canceled`, `refund.succeeded`. Возврат после формы: `/api/billing/return`. Уведомления не требуют игрового Bearer/API key; они проверяются повторным запросом к фиксированному API провайдера. Отмена и восстановление работают также при выключенных новых продажах.

Существующие продления используют цену и срок первоначального согласия. При изменении новых тарифов менять `consentVersion`, проверять новую цену в интерфейсе и получать новое согласие; существующий согласованный тариф не повышать автоматически.

Изоляция сервера: `/opt/slova`, `/var/lib/slova`, `slova-backend`, порт 8788. Ничего из `bloxx-*` не менять. `node scripts/deploy.cjs --code` сохраняет env; повторный `--apply` теперь также не перезаписывает существующий env и не печатает его содержимое.
